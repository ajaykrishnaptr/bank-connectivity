How the assistant is graded

Three graders score the same answer, and they are not interchangeable. Only one of them can reach back into the bank data to work out what the true figure was.

code proves it

Sees
The answer, and the bank data behind it.
Decides
correct: the real figure or name is in the answer. tool_used: the question reached the right tool.
Method
Expected answers are computed when the run starts, from the same tools the assistant uses, so they stay right as the daily feed adds transactions.
Costs
Nothing. No model call.

judge has an opinion

Sees
The question, the tool results, the answer.
Decides
4 pass or fail criteria plus an overall 1 to 5. Skipped on the refusal cases.
Method
A different model family from the one under test, so it never grades its own output. The prompt lives in evals/judge.py, versioned with the code.
Costs
1 call per case, free tier. Synthetic data only.

human settles it

Sees
The same answers, in a Langfuse annotation queue.
Decides
Whether the judge was right. Until this runs, the judge's agreement with a person is unmeasured.
Method
evals/review.py creates the score configs and the queue, fills it with the newest answers, and reports how often the judge and a person agree.
Status
Built, not yet run. No agreement figure exists.

The categoriser, graded a different way

Daily
The 03:00 job samples that day's transactions, creates a dataset and runs one experiment.
Benchmark
300 stratified transactions with a fixed seed, for comparing a prompt or model change side by side.
Graders
All code. category_correct for the model, rules_correct for a keyword baseline running beside it, so the model has to beat something.
Also reported
Accuracy per slice, and calibration per confidence bucket: whether a 90 to 100 confidence really is right 90 to 100% of the time.
Label firewall
evaluate.py is the only module that reads the labels. They leave the database as dataset expected outputs, which no model call ever reads.

Why the judge is not a Langfuse evaluator

Langfuse can run an LLM judge on its own servers, against experiments and against live traffic. It would take our judge model too, through an OpenAI-compatible connection. We kept it in the repository for three reasons, and one of them is not preference.

Split gradingThe figures and the tool choice are settled in code. A hosted evaluator grades the whole answer in one model call, which would fold the provable half into the opinion.
Versioned promptThe criteria move in a diff and re-run identically in CI. In the interface they move in a text box.
Key locationA hosted evaluator needs the judge's provider key stored in the Langfuse project. Today it stays on the machine that runs the experiment.
Open questionOur judge asks for json_object. A Langfuse evaluator injects json_schema, which is stricter and which some models behind a custom endpoint reject. Testable in the playground before anything is wired up.
Worth revisiting for a sampled share of live traffic, once the judge has been measured against human labels. Not before.
